01 / THE PROBLEM

Why I started it

Engineering AI needs more than a chatbot.

Physical-product development depends on revisions, interfaces, tools, calculations, source evidence, and decisions that must remain traceable long after a conversation ends.

A useful engineering agent therefore needs a shared design state, clear tool boundaries, durable execution history, and a way to distinguish a suggestion from an engineering decision.

01

Conversation is not engineering state.

Requirements, models, evidence, and changes need identity and version history outside the model's prose.

02

A tool result is not universal truth.

Every calculation or model has inputs, applicability, method versions, and limits.

03

Automation is not authority.

Agents can propose and coordinate. Engineering approval and release must stay behind explicit lifecycle gates.

02 / ARCHITECTURE

Separate the responsibilities

No single agent owns the truth.

The framework separates engineering state, execution, planning, domain semantics, external tools, and the user interface.

Canonical Engineering Models (CEMs)

Universe uses structured, versioned domain models to connect engineering properties and relationships with source evidence, assumptions, and validation results. A CEM is not one giant JSON document—and a valid model is not proof that a design is complete or approved.

05 / DESIGN PRINCIPLES

The rules I care about

Make AI useful without making engineering less accountable.

01

Agents propose. Systems record. Humans decide.

The model can help plan work, interpret context, and propose candidates. But persisted engineering state and lifecycle decisions belong to explicit system boundaries.

02

Evidence follows the inputs.

Results are bound to the model revisions, conditions, and methods that produced them. Change the basis and affected work becomes stale instead of silently remaining “true.”

03

Unknown is a valid engineering state.

Missing inputs, conflicts, assumptions, and deferred work stay explicit. The framework should stop with an owned gap rather than inventing a specification.

04

Completion is scoped.

A completed task means its requested scope is accounted for. It does not mean the whole design is correct, qualified, approved, or released.

06 / ONE EXAMPLE

Component selection

A shortlist is a proposal—not a design decision.

In one implemented workflow, requirements drive candidate discovery and screening. The task pins the requirement basis, project revision, comparison result, and exact evidence used.

If the requirement basis changes, the prior recommendation remains in history but requires re-evaluation. That is a small example of the larger idea: AI output becomes useful engineering work only when its basis is inspectable.

07 / STATUS

What it is—and what it is not

Deliberately bounded.

Implemented direction

  • Versioned engineering contracts and models
  • Core identity, revision, admission, and lifecycle foundations
  • Durable task execution and recovery
  • Bounded agent planning and provider integration
  • Domain calculations, geometry, and validation workflows
  • External-tool adapters and a native review workbench

Not claimed

  • Autonomous production-qualified engineering
  • Complete coverage of every hardware domain
  • Automatic engineering approval or release
  • Qualified physical analysis without the right models and evidence
  • Perfect round-trip fidelity with every commercial CAD tool
